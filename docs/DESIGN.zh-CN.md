# QQ Jev HUD

一个面向 Windows QQ 的只读聊天态势分析助手。

它监控当前打开的 QQ 会话，在检测到新消息后读取最近的可见对话，调用 Jev 或兼容的结构化判断服务，并把判断结果显示为锚定在对应消息旁的灰色注释卡。视觉效果接近“每条对方消息下面跟一段 Jev 判断”，但它不生成回复、不自动输入、不自动发送消息。

## 项目状态

- 当前阶段：需求与技术验证
- 目标平台：Windows 10/11
- 目标应用：Windows QQ
- 默认工作方式：只分析当前可见会话
- 模型状态：尚未配置 API Key；开发阶段必须支持模拟结果
- 已确认架构：独立 WPF 伴生程序 + 透明覆盖层，不注入 QQ 进程
- 目标视觉：尽量还原消息下方的 Jev 灰色判断卡；空间不足时切换侧边轨道

架构决策记录见 `docs/ADR-001-EXTERNAL-OVERLAY.md`。

## 核心目标

1. 自动发现并跟踪当前 QQ 聊天窗口。
2. 自动检测可见聊天内容是否出现稳定的新变化。
3. 读取最近 8～10 条可见消息，并尽量区分“我”和“对方”。
4. 一次请求完成多项结构化判断。
5. 使用逐消息锚定的透明悬浮层展示判断结果和概率。
6. 不改变 QQ，不读取 QQ 数据库，不自动发送任何内容。

## 明确不做

- 不生成候选回复。
- 不自动填写 QQ 输入框。
- 不自动发送消息。
- 不 Hook QQ、不注入 DLL、不修改 QQ 安装文件。
- 不读取本地聊天数据库或绕过平台权限。
- 不保存完整聊天记录。
- 不在日志、截图或配置文件中写入 API Key。

## 用户体验

```text
打开 QQ 会话
    ↓
程序发现 QQ 窗口并等待画面稳定
    ↓
聊天内容发生变化
    ↓
读取可见消息（优先 UI Automation，失败时使用截图 + OCR）
    ↓
去重、排序、区分双方、隐藏无关界面文本
    ↓
调用判断服务
    ↓
对应消息旁出现 Jev 注释卡
```

每张注释卡按当前消息的含义选择最有用的判断，不机械地显示全部字段。可显示：

- 对方意图
- 当前情绪
- 关系风险
- 是否值得立即回应
- 建议动作
- 对话状态
- 每项判断的概率或置信度
- 最近更新时间和数据来源（界面文本或 OCR）

注释卡默认只附着在对方消息上。用户自己的消息不重复生成卡片；当用户消息使整体局势发生明显变化时，可以更新上一张卡片中的“对话状态”。

详细布局、视觉规格和交互规则见 `docs/VISUAL-SPEC.md`。

## 第一版判断项目

### 对方意图 `intent`

候选项：

- 闲聊
- 分享信息
- 寻求帮助
- 寻求安慰
- 提出请求
- 催促
- 抱怨
- 质疑
- 拒绝
- 试探关系
- 结束对话
- 暂不明确

### 当前情绪 `emotion`

候选项：

- 平静
- 开心
- 期待
- 失落
- 焦虑
- 生气
- 尴尬
- 冷淡
- 暂不明确

### 关系风险 `relationship_risk`

五级评分：

1. 正常，无明显风险
2. 有轻微误解可能
3. 气氛紧张，需要谨慎
4. 明显冲突或边界问题
5. 高风险，建议停止自动判断并由用户自行处理

### 是否需要及时回应 `needs_response`

输出 0～1 概率。它只表示“当前消息是否期待及时回应”，不表示必须回复。

### 建议动作 `recommended_action`

候选项：

- 继续倾听
- 确认对方需求
- 表达理解
- 简短解释
- 道歉或澄清
- 设置边界
- 暂缓回应
- 结束话题
- 需要更多上下文

### 对话状态 `conversation_state`

候选项：

- 正常推进
- 正在升温
- 正在缓和
- 僵持
- 等待用户回应
- 自然结束
- 无法判断

## 自动化策略

1. 每 300～500 毫秒检查一次 QQ 窗口状态。
2. 只有聊天区域发生变化时才进入候选流程。
3. 等待内容连续稳定约 800～1200 毫秒，避免消息气泡仍在加载。
4. 对消息指纹去重，防止相同内容重复请求。
5. 只处理当前前台会话，不扫描后台联系人。
6. 切换联系人后清空旧会话的短期状态。
7. 判断请求失败时保留上一次结果，并明确显示“结果可能已过期”。

## 隐私与安全

- 默认关闭，用户主动启动后才开始观察。
- 提供明显的暂停按钮和全局暂停快捷键。
- 支持联系人白名单和排除名单。
- 本地仅保存必要设置，不保存完整聊天正文。
- 调试日志默认对聊天文本做脱敏或只保存哈希。
- 截图只在内存中处理，默认不落盘。
- API Key 仅从 Windows 用户环境变量或系统凭据存储读取。
- 模型请求前明确提示聊天内容会发送到所选服务商。
- 转账、账号、密码、身份证、地址等敏感内容应先在本地脱敏。

建议环境变量名：

```text
TYPESAFE_API_KEY
```

不要把真实密钥写进仓库、Markdown、源码或提交记录。

## 技术方案

### 推荐技术栈

- 应用框架：.NET 8 + WPF
- QQ 窗口跟踪：Win32 API
- 文本读取首选：Windows UI Automation
- 备用识别：Windows Graphics Capture + OCR
- 悬浮层：透明、置顶、不可抢占焦点的 WPF 窗口；卡片按消息气泡坐标锚定
- 网络请求：`HttpClient`
- 配置：本地 JSON，仅保存非敏感设置
- 测试：xUnit

### 模块划分

```text
src/
  QQJevHud.App/              WPF 主程序、托盘和 HUD
  QQJevHud.Windowing/        QQ 窗口发现、位置与 DPI 跟踪
  QQJevHud.Capture/          截图与可见区域获取
  QQJevHud.Accessibility/    UI Automation 文本读取
  QQJevHud.Ocr/              OCR 适配与预处理
  QQJevHud.Observer/         变化检测、稳定等待、消息去重
  QQJevHud.Analysis/         问题定义、模型调用、结果验证
  QQJevHud.Privacy/          脱敏、白名单和日志策略
tests/
  QQJevHud.Tests/
fixtures/
  public/                    不含私人聊天内容的公开测试样本
docs/
```

### 判断服务抽象

应用不应与单一服务强绑定。统一接口至少支持：

- `MockDecisionProvider`：离线开发和界面演示
- `TypeSafeDecisionProvider`：直连 TypeSafe System One API
- 以后可增加其他兼容的结构化判断服务

模型输出必须经过本地校验。未知字段、未知选项和超出范围的分数不得直接进入 UI。

## MVP 实施顺序

### 阶段 0：骨架

- 创建 .NET 解决方案和基础项目
- 建立可替换接口
- 使用模拟消息和模拟判断数据显示逐消息注释卡
- 加入托盘、暂停和退出操作

### 阶段 1：窗口跟踪

- 发现 Windows QQ 主窗口
- 跟踪移动、缩放、最小化和 DPI 变化
- 识别可见消息气泡的屏幕坐标
- 注释卡跟随对应消息移动和滚动
- 空间不足时自动切换到侧边轨道布局

### 阶段 2：读取消息

- 先验证 UI Automation 能读取哪些 QQ 元素
- 无法可靠读取时增加截图和 OCR
- 生成统一的可见消息列表
- 对截图与聊天文本默认不落盘

### 阶段 3：自动观察

- 检测新消息和联系人切换
- 稳定等待、去重和限流
- 记录不含正文的性能指标

### 阶段 4：判断层

- 先使用 Mock Provider 完成完整流程
- 接入 TypeSafe 或其他服务
- 一次请求并行询问所有独立问题
- 显示概率、置信度、错误和结果新鲜度

### 阶段 5：验证

- 使用用户自己整理并脱敏的样本测试
- 记录人工标签与模型判断差异
- 调整问题描述、选项和风险阈值
- 对高风险或低置信结果显示“无法可靠判断”

## MVP 验收标准

- 能发现并跟踪 QQ 窗口。
- 注释卡不遮挡聊天输入区域，也不抢键盘焦点。
- 注释卡能够稳定跟随对应消息；无法安全放置时缩成标记或进入侧边轨道。
- 新消息出现后，只触发一次分析。
- 切换联系人时不会混入上一个会话的内容。
- 模拟判断模式下无需密钥即可演示完整流程。
- 真实请求失败时不会崩溃或误显示为成功。
- 默认不写入聊天截图和聊天正文。
- 应用不具备发送消息的能力。

## 已知风险

- QQ 更新后界面结构和控件标识可能变化。
- OCR 可能漏字、错字或错误区分消息双方。
- 仅凭可见消息无法理解完整关系背景。
- 概率和置信度不等同于事实或心理诊断。
- 中文语境、反讽、方言和表情包可能造成误判。
- 聊天内容发送到云端模型会产生隐私风险。

## 后续可选功能

- 联系人关系备注，仅保存在本机
- 不同场景的判断模板：朋友、家人、同事、恋人
- 用户纠正结果，用于本地统计和阈值调整
- 本地模型或完全离线判断模式
- 结果历史只保存结构化结论，不保存聊天原文
- 导出脱敏后的测试报告
